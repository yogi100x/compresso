| D76 | Compaction reminder hook on by default in setup | Owner decision 2026-11-14, amending 04 §2.5. `compresso setup` installs the post-compaction routing-reminder `SessionStart`/`compact` hook for Claude Code and Codex as a second previewed plan with its own receipt; `--no-compaction-hook` opts out. | D77 | Read ceilings for compression input and repository files | Owner asked 2026-11-15 to cap the remaining unbounded reads now (E17-16); the limits below were chosen in implementation and await owner confirmation. `compresso compress` reads at most 8 MiB (the engine input limit) from stdin or `--file` and rejects more with `input_too_large` before tokenizing, never echoing it (SEC-005 remediation); previously the CLI had no limit. Repository reads stop at 16 MiB (`MAX_READ_FILE_BYTES`) and fail with `file_too_large`, including line-range reads; `compresso_context` drops the body excerpt of such a file. MCP `compresso_compress` kept its echo-back of oversized input in this change; D79 replaces it |
| D79 | Oversized MCP compression input is refused, not echoed | Owner decision 2026-11-15: proposed by the implementing session when asked to take the recommended action on the remaining SEC-005 items, then confirmed by the owner. `compresso_compress` refuses text over 8 MiB with the tool error `input_too_large` before building the context graph or counting tokens, and does not return the text. This narrows D38 for one case: fail-open exists so compression never loses or corrupts content, and here nothing is lost because the caller still holds the text it sent, while echoing it would double an input far beyond any model context and, as measured, the old path counted tokens twice first and could fail with `internal` when the tokenizer panicked. The limit and error code match the CLI (D77). Every other failure still fails open. Staleness checks hash files through a fixed 64 KiB buffer and treat a size that differs from the index as stale without reading |
| D78 | `doctor` health with warnings | Owner decision 2026-11-15. A warning state (`not_probed`, `config_modified`) never counts as healthy: the server report keeps `healthy: false`, and the check is shown as `[WARN]` with `severity: "warning"` and its fix hint. Warnings do not fail the command (`passed: true`, exit 0); only `severity: "error"` does. `healthy: true` means the server was launched and answered the probe |
| D80 | Staleness check trusts untouched files | Owner decision 2026-11-15, bounding the per-call cost of staleness checks (SEC-005). A tool call no longer hashes every indexed file. A file whose size differs from the index is stale without reading; a file with the indexed size whose modification time is at least two seconds before its `indexed_at` stamp is trusted without reading; any other file is hashed through a fixed buffer. The index stamps `indexed_at` before it reads a file, so an edit made after indexing always has a later modification time and is hashed. Accepted limits: an edit that keeps the size and also sets the modification time back to before the index is not seen until the next `compresso index`; and the comparison assumes file modification times and the indexing machine's clock agree, so where they do not (a container bind mount or network share whose clock runs behind), a same-size edit made soon after indexing can be trusted by mistake |
| D81 | `decisions --post --yes` posts through the GitHub CLI | Owner decision 2026-11-15, changing the E17-09 stub. | D85 | The context planner scans file content for concepts no symbol is named after | Proposed 2026-11-16 by the implementing session; **awaits owner confirmation**. Closes the known limit of D83: a concept written only inside a body could not enter the candidate pool, so the pack missed it and the model fell back to shell search. Decision: `plan_context` runs one bounded literal scan over the bound repository's indexed files (04 §`compresso_context`). Terms: at most eight per task — up to five compounds (those naming one to eight symbols first, then those naming none, two-word before three-word), then salient words whose own name query returned nothing. Compounds match with letter case, spaces, `_`, and `-` ignored; single words match as whole identifier words, because substring matching (`one` in `done`, `completes` through `completed`) produced a false-ready pack on an absent-concept task. A matching line maps to the smallest indexed symbol containing it; at most twelve such symbols join the pool, and a single word found in more than eight symbols adds nothing. Caps: 512 KiB per file, 2,000 files, 32 MiB read per plan. Determinism rule: the caps are counts and bytes only, with no wall-clock deadline, and files are read in index path order, so the same index and files give the same plan; reaching a cap sets `content_scan_truncated` and `truncated`. Never scanned: secret paths, text files unless the task asks for documentation, files above the per-file cap, files changed since indexing, non-UTF-8 or unreadable files, and anything outside the repository root (the existing root resolution is reused, so symlink escapes stay rejected). Reads only; no store write, schema migration, or response field. Measured on the retrieval corpus (06 §12): the two body-only tasks went from recall 0 to 1 and are now gated, three body-only tasks were added (45 corpus files, 20 gold tasks), mean recall 1.0, mean precision 0.3400 (the 15 previously gated tasks alone: 0.2557 before, 0.2478 after, because two packs gained one or two callers), false-ready 0, readiness mismatches 1; thresholds raised to recall 0.96 and precision 0.30. Measured on the twelve-task gold set over a pinned snapshot of this repository at a 1600-token budget: answering files complete for 12 of 12 tasks (was 11), mean precision 0.26 (was 0.23), ready-but-incomplete packs 0 (was 1); the `file-too-large` task went from recall 0 to 1. Cost on that snapshot (258 files, 3.4 MB scanned), release CLI, 20 runs: median 112 ms before and 140 ms after (maximum 115 and 150) in three interleaved rounds, about 1.25 times; earlier in the same session, on a busier machine, the medians were 125 and 155, so the 150 ms median target set for this change holds only on a quiet machine while the time stays well under twice the earlier one. Measured on macOS arm64 only. | E17-19 |
| D84 | Context-pack retrieval quality is a release gate | Proposed 2026-11-16 by the implementing session; **awaits owner confirmation**. Until now the eval gates measured text compression only, so a planner change that returned the wrong code could not fail CI. Decision: `compresso-eval` indexes a committed 37-file synthetic source corpus (`fixtures/retrieval/`, 06 §12) with the production indexer, runs `plan_context` at a fixed 1600-token budget for 20 developer-question tasks, and adds a `retrieval` section to the report. `gates.toml` `[retrieval]` gates four aggregates over the tasks without a `known_gap`: `mean_recall_min = 0.95` (measured 1.0 on 15 gold tasks; one fully missed task fails), `mean_precision_min = 0.22` (measured 0.2557), `false_ready_max = 0`, and `ready_mismatches_max = 1` (measured 1). Two tasks whose concept is written only inside a function body are marked `known_gap = "body_only"`, reported, and excluded; both are missed today, and a content-search change should flip them and remove the marker. Measured against the planner before E17-17 on the same corpus: precision 0.1792, 2 false-ready packs, 2 readiness mismatches, so three of the four rows fail; recall was 1.0 in both, because a 37-file corpus is small enough that every gold file is reached, so on this corpus the recall row guards against losing a file rather than measuring ranking gains. Thresholds were measured on macOS arm64 only. No schema migration; report `schema_version` stays 1 because keys are only added. | E17-18 |
| D83 | A context pack is ready only when its evidence covers the task | Proposed 2026-11-16 by the implementing session after a measured session comparison; **awaits owner confirmation**. Finding: on a twelve-task gold set over this repository, 12 of 12 packs reported `task_pack_ready` while 3 lacked the file that answers the task, and about 9% of evidence items came from an answering file; in a traced session the model received `answer_from_pack`, then ran four shell searches. Cause: one query per task word, hits interleaved by per-query rank, so a symbol matching one common word ranked with one matching the whole concept, and readiness meant only "every candidate file fitted". Decision: the planner adds compound-identifier queries, cross-query and body scoring, a test-code penalty, a noise floor, and match-centred excerpts (04 §`compresso_context`); readiness additionally requires the evidence to mention at least half of the task's salient words, reported as `task_coverage`. Measured after: answering file present for 11 of 12 tasks (was 9), on-target evidence 23% (was 9%), packs about a quarter smaller. Known limit: a concept that appears only inside symbol bodies and in no indexed name is still unreachable, because the index covers names and signatures; closing that needs bounded content search (closed by D85). No schema migration; `schema_version` stays 1 because fields are only added. | E17-17 |
| D82 | A read does work in proportion to what it returns | Owner decision 2026-11-15: proposed by the implementing session when asked to bound per-request time (SEC-005), then confirmed by the owner before the change was merged. `read` (CLI and MCP, including the gate and line ranges) no longer tokenizes a whole file to return a budgeted slice: the returned text is found through a window that grows only until the budget is exceeded, and a start-only range uses a line count. Two things change for a file or selection above 1,000,000 bytes: `file_tokens_total` is a byte-length estimate instead of the exact tokenizer count, flagged by `file_tokens_total_estimated: true`, and the overage in the `elision` text is worded "about N tokens over budget". Up to that size (every indexed file) both stay exact. Returned content is always a prefix within the budget with an exact `tokens_used`; because token counts are not strictly monotonic in prefix length, it can differ by a few bytes from what the previous search returned. Measured on a 16 MiB file: 6.9 s to 0.14 s for a log, 26.6 s to 0.29 s for unbroken text |

## 6. Owner hard constraints (never override without new owner decision)

1. No telemetry enabled, ever, without explicit opt-in decision (D6).
2. No Claude Desktop bundle/integration (D5).
3. Source code and prompt content never leave the device by default.
4. Cloud/licensing failure must never break the underlying coding assistant.
5. All assistant-config changes: preview + timestamped backup + key-level receipt + reversible uninstall.
